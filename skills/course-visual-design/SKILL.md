# Course visual and multimedia design

Read [visual and multimedia principles](references/principles.md). Respect the selected authoring format and existing brand system. All examples and interface text are English unless explicitly requested otherwise.

## Workflow

1. Identify the screen's learning purpose, intended attention order, essential task cues, and learner action. If no action is needed, a clear explanation may be better than artificial clicking.
2. Establish one project style guide: palette with semantic roles and contrast checks, type scale, grid/spacing, button states, navigation, image style, and motion policy. Explore directions for initial approval if useful; retain the approved theme across the course series.
3. Preview one representative screen per relevant layout (instruction, decision, feedback, conversation) before building repeated screens. Use content-specific visuals; do not invent credentials, metrics, or capabilities to fill space.
4. Specify any animation with its teaching purpose, initial/final state, learner trigger or timeline cue, pacing, pause/skip/replay behavior, reduced-motion/static equivalent, and accessible text alternative. Use motion to demonstrate a process, direct attention to a change, or reveal consequences. Do not add atmosphere at the expense of essential information.
5. Author a structured scene specification using registered components. A new animation may be explored in an isolated unapproved prototype, then reviewed and tested before becoming a reusable component. Do not substitute free-form page generation for the stable renderer.
6. Inspect rendered screens and relevant animation frames, mobile widths, keyboard flow, text enlargement, and reduced motion. Report not-run checks honestly. Source inspection and aesthetic scoring do not establish accessibility or learning effectiveness.

## Output

Provide style tokens, representative layout specification/preview, attention order, visual/media rationale, motion cue table where needed, accessibility alternatives, and a review table with issue/location/proposed fix. ID edits must write back to versioned project specifications; feedback collection alone does not auto-edit or approve output. Re-review affected facts, objectives, and criteria when changed.

## Boundaries

Hints are hidden until explicitly requested. Guided-practice feedback may follow a choice; AI role-play evaluation remains private until the final debrief. Do not place evaluative notes or answer clues in decorative sidebars.

The huashu-design timeline/scene separation is a useful engineering reference, not an installed dependency. Check `docs/visual-reuse-review.md` before reuse; retain licensing notices if code is copied. Its default soundtrack, cinematic styling, and repeated multi-direction exploration are not course requirements. Do not weaken contrast checks for a visual style.
